# 퇴직연금 사후관리 Agent

---

## 1. 한눈에 보는 전체 흐름

> **은행에 흩어져 있는 고객 정보가 들어왔을 때,
> "이 고객에게 지금 무엇을 관리해야 하는지"를 어떻게 판단하고,
> 직원이 바로 쓸 수 있는 상담 Brief까지 어떻게 만드는가?**

```text
① 원천 고객정보                                    [데이터]
   계좌 / 거래 / 보유상품 / 앱 행동 / 고객 기본정보
            ↓
② LLM이 판단하기 좋은 형태로 고객정보 정리                    [시스템 로직]
   각 사실에 출처·시점을 부여
            ↓
③ 날짜·금액 계산과 제약조건을 미리 확정                 [시스템 로직]
   "입금 후 20일 경과", "투자성향상 4~6등급만 권유 가능" 등
            ↓
④ "판단하려면 어떤 업무지식이 필요한가?" 결정            [LLM]
            ↓
⑤ 관련 기반지식을 넓게 찾고, 다시 좁히고, 재검사        [시스템 로직 + LLM]
   시스템이 후보 6건 검색 → LLM이 1건 제외 → 시스템이 신뢰수준 재확인
            ↓
⑥ 고객 상황과 관리 방향을 판단                          [LLM]
   "개입 필요 / 정보 안내 중심" + 고객에게 추가로 확인할 사항
            ↓
⑦ 판단 결과에 따라 상품 후보 탐색                       [시스템 로직 + LLM]
   시스템이 후보 11개 검색 → 제약 표시 → LLM이 5개로 정리
            ↓
⑧ 최종 직원용 Brief 작성                        [LLM]
            ↓
⑨ 제약·근거·상품·화면을 최종 검증                       [시스템 로직]
            ↓
     직원이 상담에 바로 쓰는 Brief
```

MOCK_001 실행에서 LLM은 총 **5번** 호출되었습니다.
판단 성격의 호출 3번(④⑥⑧)과, 검색된 후보를 정리하는 호출 2번(⑤⑦의 일부)입니다.
나머지는 전부 정해진 규칙대로 움직이는 시스템 로직입니다.

## 2. 예시 고객 — MOCK_001

### 고객 기본정보

* 만 47세, 재직 중
* 개인형IRP 가입일: 2019-03-11 (가입 약 7.5년)
* 투자성향: **위험중립형** (2026-05-14 분석, 유효)
* 퇴직급여 미포함, 스타뱅킹(모바일 앱) 이용 고객
* 총 금융자산 2억 1,000만원 / 당행 조회 범위 내 타 연금계좌 없음

### 현재 IRP 계좌

* 총 평가금액 **5,800만원**
  * 현금성자산 **3,000만원**
  * 정기예금(2년제) 2,000만원 — 만기 2027-04-10, 가입 시 약정금리 연 3.1%
  * 채권형 펀드(위험등급 6등급) 800만원
* **디폴트옵션(사전지정운용제도) 미등록**
* 당해년도 개인부담금 납입액 0원

### 최근 변화

* **2026-08-08, 타 금융기관 IRP 계약이전으로 3,000만원 입금**
* 참고: 한 달 전(2026-07-29) 스냅샷에는 현금성자산 0원 / 전체 2,800만원

### 최근 앱 행동

* 8/19 스타뱅킹에서 IRP 수익률 화면 조회
* 8/22 상품찾기에서 펀드 목록 조회
* 8/25 TDF 상품 상세 화면 조회
* **세 번 모두 조회만 했고 실제 매수 실행은 없음**

### 여기서 가장 중요한 점

원천 데이터에는 **판단 문구가 하나도 없습니다.**
"자금 방치 중", "TDF 가입 의향 있음", "리밸런싱 필요", "상품 추천 필요" 같은 말은 어디에도 들어있지 않습니다.
원천 데이터는 **관찰 가능한 사실만** 제공하고,
"이 사실들이 무엇을 의미하는가"는 이후 단계에서 근거와 함께 만들어집니다.

## 4. 정제 과정: 입력 데이터 → 정제 → 9개 블록 → 제약조건 검사

원천 데이터는 LLM에 바로 들어가지 않습니다. 시스템 로직이 다음 순서로 정제합니다.

```text
입력 데이터 (위 스키마)
        ↓
[정제]  모든 사실을 번호 붙은 문장으로 변환 — 18건 (E001~E018)      [시스템 로직]
        각 사실에 함께 보존:
        · 번호 (E001…)      → 판단 근거를 원천까지 역추적하기 위함
        · 성격              → [F] 확정 사실 / [S] 행동 신호 (조회 ≠ 의사)
        · 출처              → 계좌 시스템 / 거래내역 / 앱 행동 로그 / 외부 계좌
        · 시점              → 잔액은 8/28 기준, 입금은 8/8 발생 등
        ↓
[계산]  계산으로 확정 가능한 것은 시스템이 먼저 계산 — 6건 (D001~D006)  [시스템 로직]
        · [A] 산술 파생:  입금 후 20일 경과 / 30일간 현금 +3,000만원 /
                          현재 현금과 입금액 금액 일치(산술 대조) / 정기예금 만기 D-225
        · [R] Rule 판정:  연금개시요건 미충족 (만 55세+가입 5년 기준, 근거 규칙 병기)
        ↓
[9개 블록]  E + D 24건을 9개 블록의 고객정보 한 장으로 조립          [시스템 로직]
        ↓
[제약조건 검사]  판단 전에 넘을 수 없는 한계선을 확정                [시스템 로직]
```

### 변환 예시 (실제 MOCK_001)

```text
원천:  balance_total = 58,000,000 / balance_cash = 30,000,000
  ↓
[E006][F] IRP 평가금액: 58,000,000원 (현금성자산 30,000,000원 포함)   ·계좌 시스템 ·8/28 기준
```

```text
원천:  2026-08-25 / 스타뱅킹 TDF 상품 상세 화면 조회 / executed = false
  ↓
[E016][S] 2026-08-25 스타뱅킹 TDF 상품 상세 화면 조회 (실행 이력 없음)  ·앱 행동 로그
```

번호를 붙이는 이유: 뒤 단계의 모든 판단은 "근거: E009, D004, E014~E016"처럼 번호를 인용해야 하고,
존재하지 않는 번호를 근거로 쓰면 최종 검증에서 탈락합니다.

정제·계산 단계의 원칙은 **의미판단 금지**입니다. 코드 차원에서 "방치·미운용" 같은
의미 단어의 사용이 금지되어 있습니다(단위 테스트로 강제).

```text
시스템이 말할 수 있음:  "입금 후 20일이 지났다"                        (달력 계산)
시스템이 말하면 안 됨:  "20일 동안 방치됐다"                           (의미 판단 → LLM 몫)

시스템이 말할 수 있음:  "현금 3,000만원과 최근 입금액이 금액상 일치한다"  (산술 대조)
시스템이 말하면 안 됨:  "투자하려고 이전해 온 돈이다"                    (의도 추정 → 확인 사항)
```

### 9개 블록 — LLM에 전달되는 고객정보 한 장의 구조

| 블록 | 내용 | MOCK_001 |
|---|---|---|
| ① 고객·연금 생애주기 | 연령, 가입일, 재직, 투자성향 + 연금개시요건 판정 | E001~E005, D006 |
| ② 현재 IRP 스냅샷 | 평가금액, 보유상품, 디폴트옵션, 납입액 | E006~E010 |
| ③ 최근 변화·자금 흐름 | 과거 스냅샷 + 증감·경과일·금액 대조 계산 | E011, D001~D004 |
| ④ 이벤트 타임라인 | 입출금 거래 | E012 |
| ⑤ 투자 행동 | 최근 1년 매매 이력 | E013 |
| ⑥ 디지털 행동 | 앱 조회·검색 (경계 문구: "행동은 관심 신호일 뿐 고객 의사가 아니다" 명시) | E014~E016 |
| ⑦ 전체 금융 맥락 | 총 금융자산, 타 연금계좌 | E017~E018 |
| ⑧ 다가오는 결정 시점 | 만기 D-n 등 | D005 |
| ⑨ 사람이 쓴 보조 맥락 | CRM 메모 (경계 문구와 함께, 고객 의사 확정 근거 아님) | 없음 |

### 제약조건 검사 — 판단 전에 확정되는 한계선

고객 투자성향(위험중립형)에서 시스템이 기계적으로 도출합니다. LLM은 이 범위를 바꿀 수 없습니다.

```text
고객 투자성향: 위험중립형
  ↓
C1  제안 가능한 위험수준:   안정형 / 안정추구형 / 위험중립형   (적극·공격투자형 금지)
C2  권유 가능한 펀드 등급:  4등급(보통) ~ 6등급(매우낮은위험)   (1~3등급 금지)
C3  가입 가능한 디폴트옵션: 지켜드림·알파드림·뿔려드림          (고위험 '모두드림' 금지)
```

> **투자성향은 "이 수준까지 위험상품을 추천하라"는 목표가 아니라, 넘을 수 없는 최대 위험한도입니다.**
> 더 낮은 위험의 운용은 언제나 허용되며, "성향보다 안전하게 운용 중"이라는 사실만으로
> 변경 필요를 판정하지 않습니다.

이 제약은 이후 모든 LLM 호출에 함께 전달되고, 마지막 단계(⑨ 최종 검증)에서
같은 기준으로 다시 한 번 기계적으로 검사됩니다 — LLM이 실수해도 출력 전에 걸러집니다.
MOCK_001은 최종 검증 8종을 전부 통과했습니다.
