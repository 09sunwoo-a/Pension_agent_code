## 1. 한눈에 보는 전체 흐름

> **은행에 흩어져 있는 고객 정보가 들어왔을 때,
> "이 고객에게 지금 무엇을 관리해야 하는지"를 어떻게 판단하고,
> 직원이 바로 쓸 수 있는 상담 Brief까지 어떻게 만드는가?**


```text
① 원천 고객정보 수집                                   [데이터]
   계좌 / 거래 / 보유상품 / 앱 행동 / 고객 기본정보
            ↓
② 판단하기 좋은 형태로 고객정보 정리                    [시스템 로직]
   각 사실에 번호(E001~E018)와 출처·시점을 부여
            ↓
③ 날짜·금액 계산과 제약조건을 미리 확정                 [시스템 로직]
   "입금 후 20일 경과", "투자성향상 4~6등급만 권유 가능" 등
            ↓
④ "판단하려면 어떤 업무지식이 필요한가?" 결정            [LLM]
            ↓
⑤ 관련 기반지식을 넓게 찾고, 다시 좁히고, 재검사        [시스템 로직 + LLM]
   시스템이 후보 6건 검색 → LLM이 1건 제외 → 시스템이 신뢰수준 재확인
            ↓
⑥ 고객 상황과 관리 방향을 판단                          [LLM]
   "개입 필요 / 정보 안내 중심" + 고객에게 확인할 사항
            ↓
⑦ 판단 결과에 따라 상품 후보 탐색                       [시스템 로직 + LLM]
   시스템이 후보 11개 검색 → 제약 표시 → LLM이 5개로 정리
            ↓
⑧ 최종 직원용 Brief(S1~S5) 작성                        [LLM]
            ↓
⑨ 제약·근거·상품·화면을 최종 검증                       [시스템 로직]
   8종 자동 검사 — MOCK_001은 전부 통과
            ↓
     직원이 상담에 바로 쓰는 Brief
```

## 4. 2단계: LLM이 판단하기 좋은 고객정보로 정리

원천 데이터는 LLM에 바로 들어가지 않는다.
먼저 시스템 로직이 모든 사실을 **한 건씩 번호가 붙은 문장**으로 변환합니다.

실제 변환 전/후 예시입니다.

```text
원천:  balance_total = 58,000,000 / balance_cash = 30,000,000
  ↓
[E006] IRP 평가금액: 58,000,000원 (현금성자산 30,000,000원 포함)
```

```text
원천:  2026-08-08 / 입금 / 30,000,000 / 타 금융기관 IRP 계약이전 입금
  ↓
[E012] 2026-08-08 입금 30,000,000원 (사유: 타 금융기관 IRP 계약이전 입금)
```

```text
원천:  do_registration.registered = false
  ↓
[E009] 디폴트옵션 등록 여부: 미등록
```

```text
원천:  2026-08-25 / 스타뱅킹 TDF 상품 상세 화면 조회 / executed = false
  ↓
[E016] 2026-08-25 스타뱅킹 TDF 상품 상세 화면 조회 (실행 이력 없음)
```

```text
원천:  holdings[0] = KB퇴직연금 정기예금(2년제), 20,000,000, 만기 2027-04-10
  ↓
[E007] 보유상품: KB퇴직연금 정기예금 (2년제) 20,000,000원
       (만기 2027-04-10, 가입 시 약정금리 연 3.1%)
```


각 사실에는 다음 정보가 같이 붙습니다.

* **이것이 확정된 사실인가, 행동 신호인가** — 예를 들어 "평가금액 5,800만원"은 사실(fact)이지만,
  "TDF 화면을 조회했다"는 관심을 추정할 수 있는 신호(signal)일 뿐.
* **어느 시스템에서 온 정보인가** — 계좌 시스템, 거래내역, 앱 행동 로그, 외부 계좌 정보.
* **어느 시점 기준인가** — 잔액은 2026-08-28 기준, 입금은 2026-08-08 발생처럼 시점을 보존합니다

## 5. 3단계: 계산 가능한 사실과 제약조건을 미리 계산한다

### 5-1. 시스템이 미리 계산하는 사실

날짜 차이, 잔액 증감처럼 **계산으로 확정할 수 있는 것은 LLM에게 시키지 않고 시스템이 먼저 계산**합니다.

| 번호 | 시스템이 계산한 사실 |
|---|---|
| D001 | 2026-08-08 계약이전 입금 3,000만원 → **기준일까지 20일 경과** |
| D002 | 최근 30일 현금성자산 증감: **+3,000만원** (0원 → 3,000만원) |
| D003 | 최근 30일 전체 평가금액 증감: +3,000만원 (2,800만원 → 5,800만원) |
| D004 | **현재 현금성자산 3,000만원은 8/8 계약이전 입금액과 금액이 일치** (산술 대조) |
| D005 | 정기예금 2,000만원 만기 2027-04-10 → **D-225** |
| D006 | 연금개시요건 **미충족** (만 47세, 가입 7.5년 — "만 55세 이상 + 가입 5년 이상" 행내 공식 기준으로 판정) |

### 5-2. 계산과 의미판단의 경계

시스템의 핵심 설계 원칙
**계산과 의미판단을 분리**합니다.

```text
시스템이 말할 수 있음:   "입금 후 20일이 지났다"                    (달력 계산)
시스템이 말하면 안 됨:   "20일 동안 방치됐다"                       (의미 판단)
```

```text
시스템이 말할 수 있음:   "현금 3,000만원과 최근 입금액이 금액상 일치한다"  (산술 대조)
시스템이 말하면 안 됨:   "이 돈은 고객이 투자하려고 이전해 온 돈이다"      (의도 추정)
```

무엇을 의미하는지는
뒤 단계에서 업무지식을 근거로 LLM이 판단.

### 5-3. 투자성향 등 사전 제약조건

```text
고객 투자성향: 위험중립형
  ↓  시스템이 사전에 허용 범위 계산
  ↓
· 제안 가능한 위험수준:  안정형 / 안정추구형 / 위험중립형          ← 허용
· 제안 금지 위험수준:    적극투자형 / 공격투자형                    ← 금지
· 권유 가능한 펀드 위험등급:  4등급(보통)~6등급(매우낮은위험)만
· 가입 가능한 디폴트옵션:  지켜드림·알파드림·뿔려드림 (고위험 "모두드림"은 불가)
```

## 6. 4단계: AI가 판단에 필요한 지식을 정한다 (LLM 호출)

**들어오는 정보**

* 정리된 고객정보 18건 + 시스템 계산 결과 6건

**하는 일**

* "이 고객의 상태를 판단하려면 어떤 제도·업무 지식을 확인해야 하는가"라는 **질문 목록**만 생성

```text
이 고객을 판단하려면…

[질문 1]  타 금융기관 IRP에서 계약이전으로 들어온 입금액에
          디폴트옵션이 언제 적용되는지, 어떤 운용 규칙이 적용되는지 확인 필요
          (근거로 지목한 사실: 디폴트옵션 미등록 E009, 입금 후 20일 경과 D001,
           현금과 입금액 일치 D004, 계약이전 입금 E012)

[질문 2]  IRP 계좌의 현금성자산으로 상품을 매수하거나 교체할 때
          앱에서 어떤 경로로 실행하는지 확인 필요
          (근거로 지목한 사실: 평가금액 구성 E006, 앱 조회 행동 E014~E016)
```

## 7. 기반지식은 어떻게 준비되어 있는가


| 저장소 | 담고 있는 것 | 규모 |
|---|---|---|
| ① 공식·업무 지식 (OK) | 퇴직연금 제도·업무처리 기준 — 가입·수령·이전·디폴트옵션·세제 등 | 17건 |
| ② 상품 정보 (PRD) | 상품명, 유형, 위험등급, 수익률과 기준일, 만기 등 상품 자체의 사실 | 22건 |
| ③ 현장 활용 팁 (HT) | 직원이 상담·처리에서 활용하는 경험적 노하우 | 별도 저장 |
| ④ 상담 화법 (TALK) | 특정 상황에서 참고할 수 있는 상담 표현 원문 | 별도 저장 |
| ⑤ 업무 화면 / 실행 경로 (SCR) | 직원 단말 화면번호·앱 메뉴 경로 — 실제로 어디서 처리하는가 | 23건 |
| ⑥ 확인되지 않은 지식 (KG) | 필요하지만 현재 확보한 자료로 확정할 수 없는 사항의 기록 | 별도 저장 |

### 기반지식은 어떻게 만들어졌는가

원천은 행내 업무가이드, 퇴직연금 교육자료, 상품자료, 현장 Hot Tip, 상담자료, 화면 매뉴얼 등입니다.
이 문서들을 통째로 넣지 않고, 다음 과정을 거쳐 **작은 지식 단위**로 정리.

```text
행내 업무가이드 / 교육자료 / 상품자료 / Hot Tip / 상담자료 / 화면 매뉴얼
        ↓
   내용을 그대로 거대한 문서로 넣지 않음
        ↓
   각 지식 단위마다 함께 정리:
   · 무슨 사실인가?                       (내용)
   · 어디에서 나온 내용인가?              (출처 — 원문 위치까지)
   · 언제 기준인가?                       (기준 시점 — 금리·수익률은 필수)
   · 확정적으로 써도 되는가?              (공식 기준 / 행내 가이드 / 현장 팁 / 공개자료 구분)
   · 어떤 경우에는 쓰면 안 되는가?        (한계 — 모든 공식 지식에 필수 기재)
        ↓
   Agent가 필요한 부분만 선택해 쓸 수 있는 지식 단위로 저장
```

## 8. 5단계: 필요한 지식을 "넓게 찾고, 다시 좁히는" 과정

> **시스템은 넓게 찾고, LLM은 의미를 보고 좁히고, 시스템이 마지막으로 신뢰범위를 통제한다.**

### 1단계 — 시스템이 관련 가능성이 있는 지식을 넓게 찾음 `시스템 로직`

검색된 후보 6건:

| 후보 | 내용 (한 줄 요약) |
|---|---|
| OK-002 | 개인형IRP 계약이전 **전출**(당행→타행 이탈) 접수 시 처리 절차 |
| OK-003 | 계약이전의 실물/현금 이전 구조, 부분이전 절차는 미확인이라는 사실 |
| OK-004 | 정기예금 만기 처리 — 자동 재예치 폐지, 만기자금은 현금성자산으로 대기 |
| OK-005 | **디폴트옵션 적용 시점 규칙(입금 후 2주 / 만기 후 6주 / 옵트인)과 미등록 계좌의 처리** |
| KG-002 | "부분이전 실행 경로"는 현재 자료로 확인되지 않는다는 기록 |
| OK-012 | 위험자산 투자한도 70% 규칙과 예외(TDF 등) |

### 2단계 — LLM이 맥락을 보고 불필요한 후보를 제거 `LLM 호출 (정리용)`

LLM에게 지식 질문과 후보 목록(제목·주제어 요약만)을 주고,
**현재 고객 상황과 지식의 실제 의미를 비교해 명백히 불필요한 것만** 제거


```text
후보 중 'OK-002'가 키워드 "계약이전"으로 검색됨
        ↓
LLM 확인
        ↓
이번 질문은 "타 금융기관 → 당행으로 들어온 계약이전 입금액"의 규칙인데,
OK-002는 "당행 → 타 금융기관으로 나가는 전출(이탈)" 업무를 다룸
        ↓
같은 "계약이전"이라는 단어를 쓰지만 방향이 반대 → 이번 판단에는 불필요, 제외
```

LLM이 남긴 실제 제외 사유(기록 원문):
*"KN-M01은 계약이전 입금액(전입) 및 디폴트옵션 규칙을 다루나, 해당 항목은 전출(이탈) 절차를 다루므로 주제가 다름"*

나머지 5건(OK-003, OK-004, OK-005, KG-002, OK-012)은 유지


## 9. 6단계: AI가 고객 상황과 관리 방향을 판단한다 (LLM 호출 2)

이제 두 번째 판단 성격의 LLM 호출입니다. 입력은 다음과 같이 조립됩니다.

```text
정리된 고객정보 (E001~E018)
   +
시스템 계산 결과 (D001~D006)
   +
투자성향 등 사전 제약 (허용/금지 범위)
   +
이번 고객에게 필요한 것으로 선택된 업무지식 5건 (K-001~K-005, 한계 포함)
```

이를 보고 LLM이 수행하는 일:

1. 고객의 현재 상황을 **사실과 추론을 구분해** 해석하고
2. 지금 관리가 필요한지, 왜 필요한지 판단하고
3. 행동하기 전에 고객에게 **먼저 확인해야 할 것**을 정리하고
4. 확인 결과에 따라 어떤 방향을 제시할 수 있는지 **조건부로** 결정

이 호출에도 원칙이 명시됩니다: 신호(앱 조회)는 의사가 아니다 /
어느 방향도 기본값이 아니다 / 지식·근거에 없는 제도 사실을 만들지 않는다 /
고객 확인 전에 방향을 확정하지 않는다 / 은행의 영업 목적을 관리 필요성의 근거로 쓰지 않는다.
그리고 **이 단계에서는 상담 화법과 최종 상품 추천을 만들지 않습니다.**

### MOCK_001의 실제 판단 결과 (기록 요약)

**상황 해석** — 기록 원문이 사실과 추론을 스스로 구분합니다.

* 사실: 8/8 계약이전으로 3,000만원 입금(E012, D001), 현재 그 금액이 현금성자산으로 보유(E006, D004),
  디폴트옵션 미등록(E009), 최근 수익률→펀드→TDF 순 조회 이력(E014~E016)
* 추론: 선택된 지식 K-003(디폴트옵션 적용 규칙)에 따르면 미등록 계좌는 별도 운용지시가 없으면
  자금이 현금성자산으로 계속 대기하므로, 입금 후 20일이 지난 현재까지 운용되지 않은 상태.
  상품 조회 행동은 (신호로서) 운용에 관심이 있는 것으로 추정됨.

**관리 판단**

> **"개입 필요 / 정보 안내 중심"**
> — 이전 입금액 3,000만원이 디폴트옵션 미등록으로 현금성 대기 중이고,
> 최근 상품 조회 행동이 관찰되어 운용 방향 안내와 제도적 보완(디폴트옵션 등록) 안내가 필요한 시점

**행동 전 확인 필요 사항** — 판단이 여기서 멈추는 것이 핵심입니다.

* 현금성자산 3,000만원에 대한 고객의 구체적 운용 의사와 상품 선호
* 디폴트옵션 등록 의사

**관리 방향** — 확인 결과에 따른 조건부 2갈래.

| 조건 | 방향 |
|---|---|
| 고객이 직접 상품을 선택해 운용하려는 경우 | 투자성향(위험중립형)과 펀드 위험등급 제한(4~6등급) 범위 내 상품 매수 안내 |
| 상품 결정이 어렵거나 자동 운용을 원하는 경우 | 디폴트옵션 제도 안내, 가입 가능 포트폴리오(지켜드림·알파드림·뿔려드림) 등록 지원 |

**상품 재료 필요 여부** — 다음 단계로 넘기는 주문서입니다.

* 필요함. ① 직접 운용 지원용: TDF / 채권형 펀드 / 정기예금 / GIC(이율보증형보험) 유형
  ② 디폴트옵션 적용용: 초저위험(지켜드림)·저위험(알파드림)·중위험(뿔려드림)

### MOCK_001에서 중요한 판단 포인트 — 단순 규칙과 무엇이 다른가

확인된 사실만 보면 이렇게 요약됩니다.

```text
- 3,000만원 계약이전 입금 (20일 경과)
- 현재 현금성자산 3,000만원 (입금액과 금액 일치)
- 디폴트옵션 미등록
- 최근 수익률 → 펀드 목록 → TDF 상세 순서로 조회
- 실제 매수는 없음
```

단순 규칙이라면 "TDF 조회 3회 → TDF 추천"으로 직행할 수 있는 상황입니다.
하지만 이 Agent는 **"고객은 TDF를 사고 싶다"고 판단하지 않았습니다.**

* 앱 조회는 관심 **신호**일 뿐, 운용 **의사**가 아닙니다 (시스템 원칙에 명시).
* 그래서 첫 번째 행동은 추천이 아니라 **"운용 의사를 고객에게 확인"**입니다.
* 방향은 "직접 운용을 원하면 A / 자동 운용을 원하면 B"의 **조건부**로만 구성됩니다.
* "20일 경과"(계산)와 "운용되지 않고 대기 중"(지식 기반 추론)이 구분되어 기록됩니다.
  "대기 중"이라는 해석은 임의 판단이 아니라 "미등록 계좌 자금은 지시 전까지 현금성으로 대기한다"는
  공식 지식(K-003)을 인용한 추론입니다.

## 10. 7단계: 필요한 경우 상품 후보를 찾는다

### 순서가 중요합니다

이 시스템에서 상품은 **고객 판단이 끝난 뒤에** 등장합니다.

```text
❌ 이런 순서가 아님:   상품 검색 → 고객에게 추천할 이유 만들기

✅ 실제 순서:          고객 상황 판단 → 관리 방향 결정
                       → 필요한 상품의 조건 결정 → 그 조건에 맞는 후보 검색
```

### 상품 후보를 찾는 방법

지식 검색과 같은 3단 구조인데, 상품에는 **추가 제약**이 있습니다.

```text
필요한 상품 조건 (유형: TDF / 채권형 펀드 / 정기예금 / GIC …)
        ↓
① 상품정보 저장소에서 유형이 맞는 후보를 넓게 찾음                  [시스템]
   + 카드 완결성 검사: 실명 상품인가? 위험등급 있는가?
     수익률과 기준일이 있는가? (미달이면 후보 제외 + 사유 기록)
        ↓
② 각 후보에 투자성향 대비 권유 가능 여부를 표시                     [시스템]
   (위험중립형 → 4등급 이상만 "권유 가능" 표시)
        ↓
③ LLM이 비슷한 후보 중 의미 있는 후보만 남김                        [LLM]
   (차별점 없는 단순 중복 제거 — 단, 유형 통째 삭제 금지,
    수익률 높다는 이유로 대표 선정 금지, 최종 추천 결정 금지)
        ↓
최종 상품 후보군  (위험등급 차단은 이후 검증 단계가 다시 수행)
```

### 실제 결과

**③ LLM 정리 후 최종 후보: 5개**

| 유지 | 제거 (실제 기록된 사유) |
|---|---|
| P01 KB 온국민 TDF 시리즈 | P02 신한 · P03 한화 — "TDF 동일 위험등급(3) 내 단순 중복" |
| P04 마이다스 기본 TDF 시리즈 (4등급) | |
| P05 DB손해보험 GIC (3년) | P06·P07·P09·P11 — "GIC 동일 만기(3년) 내 단순 중복" |
| P08 메리츠화재 GIC (5년) | |
| P10 KB손해보험 GIC (2년) | |

남긴 결과를 보면 정리 기준이 드러납니다:
TDF는 위험등급이 서로 다른 것(3등급 대표 1개 + 4등급 1개)을,
GIC는 만기가 서로 다른 것(2년/3년/5년)을 남겨 **선택지의 다양성**을 보존했습니다.

## 11. 8단계: 직원용 Brief를 만든다 (LLM 호출 3)

마지막 판단 성격의 LLM 호출입니다. 앞 단계의 모든 결과가 입력으로 들어갑니다.

```text
정리된 고객정보 + 시스템 계산 + 사전 제약
   + 선택된 업무지식 5건
   + 앞 단계의 관리판단·확인사항·관리방향 (이 판단과 일관되게 쓰되, 미확인 사항의 조건성 유지)
   + 최종 상품 후보 5개 (수치는 저장소 값 그대로)
   + 사용 가능한 업무 화면 2개
```

출력은 직원이 상담에서 그대로 쓰는 Brief로, 다섯 부분으로 구성됩니다.

* **S1. 고객 상황** — 지금 이 고객에게 어떤 일이 있는가
* **S2. 핵심 관리 포인트** — 이번 상담에서 무엇을 확인하고 관리해야 하는가.
  이때 "직원이 상담 전에 시스템에서 확인할 것"과 "고객에게 직접 확인할 것"을 분리
* **S3. 관리 방향 / 제안** — 확인 결과에 따라 어떤 방향을 제시할 수 있는가. 상품 후보는 여기에 등장
* **S4. 상담 화법** — 실제로 어떻게 말을 시작하고 이어갈 것인가
* **S5. 업무 지원** — 어떤 화면에서 확인·처리할 것인가

### MOCK_001의 실제 최종 Brief

아래는 실행 기록에 저장된 **실제 출력 원문**입니다 (표현을 다듬지 않고 그대로 옮겼습니다).

#### S1. 고객 상황

> 2026년 8월 8일 타사 IRP 계약이전으로 3,000만원이 입금되었으나, 현재 디폴트옵션이 미등록된 상태여서 해당 금액이 운용지시 없이 현금성자산으로 보유 중입니다. 최근 고객님께서 스타뱅킹을 통해 수익률과 펀드, 특히 TDF 상품 상세 화면을 조회하신 이력이 확인되어 자산 운용에 관심이 높으신 상황으로 보입니다.

#### S2. 핵심 관리 포인트

> 이전 입금된 3,000만원이 현금성 상태로 대기 중인 상황에서 고객의 상품 탐색 행동이 포착되었으므로, 직접 운용 또는 디폴트옵션 등록 등 적절한 운용 방향을 안내하는 것이 핵심입니다.

**상담 전 확인 (직원이 시스템에서)**

> * 단말에서 현금성자산의 정확한 잔액과 현재 수익률 현황 확인

**고객과 확인**

> * 입금된 3,000만원에 대한 구체적인 운용 계획 및 디폴트옵션 등록 의사 확인

#### S3. 관리 방향 및 상품 후보

| 조건 | 방향 | 유형 |
|---|---|---|
| 고객이 직접 상품을 선택하여 운용하고자 하는 경우 | 위험중립형 성향에 적합한 상품 매수 안내 | TDF 및 펀드 매수 |
| 운용 상품 결정에 어려움을 느끼거나 자동 운용을 원하는 경우 | 디폴트옵션 등록 지원 | 디폴트옵션 포트폴리오 지정 |

상품 후보 (앞 단계 후보군 5개 중 Brief가 제시한 2개):

> * **P04 (마이다스 기본 TDF 시리즈)** —
>   ① 고객의 TDF 상품 조회 행동이 확인되었으며, 위험등급 4등급(보통)으로 고객의 투자성향(위험중립형) 범위 내에서 운용 가능함
>   ② 은퇴 시점에 맞춘 글로벌 자산배분 특성이 IRP 장기 운용 목적에 적합함
> * **P10 (KB손해보험 퇴직연금 이율보증형보험, 2년)** —
>   원리금 보장 상품을 선호할 경우, 2년 계약기간의 이율보증형보험으로 안정적인 운용 가능

#### S4. 상담 화법

> 고객님, 지난 8월 8일에 타사에서 IRP 3,000만원을 이전해 오셨는데, 현재 이 자금이 별도의 운용지시 없이 현금성자산으로 보유되어 있어 안내차 연락드렸습니다.

> 최근 앱에서 TDF 상품 등을 살펴보신 것으로 보이는데, 혹시 이번에 이전하신 자금에 대해 생각하고 계신 운용 방향이나 특별히 선호하시는 상품군이 있으실까요?

조건부 화법:

> * [직접 운용을 희망하는 경우] 고객님의 위험중립형 투자성향에 적합하면서도, 은퇴 시점에 맞춰 자동으로 자산비중을 조절해 주는 TDF 상품(P04 등)을 검토해 보시는 것을 추천드립니다.
> * [상품 선택이 어렵거나 자동 운용을 원하는 경우] 어떤 상품을 고를지 고민되신다면, 미리 정해진 포트폴리오로 자동 운용되는 '디폴트옵션' 제도를 활용해 보시는 것이 좋습니다. 고객님은 '지켜드림', '알파드림', '뿔려드림' 세 가지 포트폴리오 중 하나를 선택해 등록하실 수 있습니다.

#### S5. 업무 지원

> * **S02** (스타뱅킹: 전체메뉴 > 가입상품관리 > 퇴직연금 > 변경관리 > 보유상품변경) — 고객이 직접 상품을 선택할 경우 매수 실행을 지원하기 위함
> * 현장 팁: 이번 Mock에서는 팁 자동 선택을 붙이지 않아 비어 있음 (정상)

## 12. 9단계: 마지막으로 결과를 검증

Brief가 만들어졌다고 바로 직원에게 전달되는 것이 아닙니다.
시스템이 **정해진 규칙으로 마지막 검사**를 수행합니다. LLM은 관여하지 않습니다.

```text
최종 확인 항목

✓ 고객 투자성향(위험중립형)을 넘어서는 위험수준을 제안하지 않았는가?
✓ 권유 불가 펀드 등급(1~3등급)의 상품을 제안하지 않았는가?
✓ 가입 불가 디폴트옵션(고위험 '모두드림')을 안내하지 않았는가?
✓ 앞 단계에서 검색된 상품 후보군 안에서만 제안했는가?
  (판매 불가 표시 상품, 후보 밖 상품이 끼어들지 않았는가?)
✓ 존재하지 않는 사실 번호(E/D)를 근거로 들지 않았는가?
✓ 확인되지 않은 내용을 확정적으로 말하지 않았는가?
  (예: "방치" 같은 확정 판단 단어가 Brief에 들어가면 자동 탈락)
✓ 실제 제공된 업무화면만 안내했는가? (없는 화면번호를 만들어내면 자동 탈락)
```
